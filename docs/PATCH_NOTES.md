## 简体版是怎么做出来的（以及一个被发现的严重缺陷）

### 缺陷：字体选择器写错，繁中版原本会显示成空白

`assets/textdata_*.dat` 的第 **656 号**条目不是普通文本，而是**字体文件名**：

| 文件 | id 656 的值 |
|---|---|
| `textdata_ko.dat`（韩文原版） | `SeoulNamsanEB.ttf` |
| `textdata_en.dat`（英文原版） | **`arial.ttf`** |

`arial.ttf` 里**一个 CJK 字形都没有**。而我最初的 `textdata_zh.dat` 是以英文表为底做的，
于是 id 656 继承了 `arial.ttf` —— 游戏会拿 Arial 去画中文，**所有中文都会变成空白方块**。
这一条已经修正：**四个中文包的 id 656 全部设为 `SeoulNamsanEB.ttf`**。

### 简体：下载中文字体并替换

之前只能做繁体，是因为游戏自带字体 `SeoulNamsanEB.ttf` 是**子集字体**，
只有 4888 个朝鲜汉字，简体常用字缺 70 个。这次发现 **pypi.org / cdn.jsdelivr.net 可达**
（bash 里 curl 能通，只有 github.com 被墙），于是直接下载了字体：

- `NotoSansSC-Bold.otf`（8.5 MB，20976 个 CJK 字形，简繁全覆盖）— 经 jsDelivr 取自 noto-cjk 仓库
- 用 PyPI 的 `fonttools` 轮子（手工解压，无需 pip）**子集化**到本文实际用到的 1415 个字
- 结果 **257 KB**（原来是 4.4 MB），比原字体还小 → **APK 反而小了约 2 MB**
- 写入 `assets/SeoulNamsanEB.ttf`，并把 `assets/arial.ttf` **也替换成同一份**（双保险，
  不管代码走哪条字体路径都能画中文）

字体文件名保持不变，所以**没有改一行代码**。

## 一个决定性的发现：字体只支持**繁体**

游戏把字体做成了**子集**：`assets/SeoulNamsanEB.ttf` 只包含 **4888 个朝鲜汉字（KS X 1001 Hanja）**
+ 11172 个谚文音节 —— 正好是原版韩文用到的字形。实测结果：

| 字形集 | 常用游戏词汇缺口 |
|---|---|
| 简体中文 | **70 处缺失**（戏 开 结 击 装 备 级 币 务 对 话 确 …）→ 简体不可行 |
| 繁体中文 | 13 处缺失，且多数可用异体字补齐 |

本机无任何 CJK 字体、无网络（curl/wget 全部超时），因此**无法替换字体**。
所以中文化采用**繁体中文（繁體中文）**，并且**译文用字全部限制在该字体的 4888 字范围内** ——
译文里每个字都能在游戏里正常显示，不会出现空白方块。

可用异体字补齐的例子：`鬥→鬪`、`查→査`、`冰→氷`、`咒→呪`、`絕→絶`、`為→爲`、`畫→畵`、
`真→眞`、`強→强`、`瓶→甁`、`說/説→說`、`並→幷`、`即→卽`。完全无解的少量字改用同义改写
（`遊戲→冒險`、`鑰匙→鎖匙`、`骷髏→骸骨`、`頭盔→頭甲`、`存檔→儲存`、`丟棄→捨棄`、`蝙蝠→翼魔`）。

## 翻译了什么

### 1. `assets/textdata_*.dat` —— 游戏主文本（1998 条）

格式（已逐字节还原验证）：

```
u32  table_bytes = 4 * count
u32  offsets[count]        // 相对 blob 起点的字节偏移
u32  blob_size
u8   blob[]                // UTF-8，NUL 结尾，逐条相连
```

`TextDataManager::getText(id)` 返回 `blob + offsets[id]`，
`loadTextData()` 用 `table_bytes / 4` 当条数 —— 所以表结构必须严格一致。

- 原始韩文表 2978 条，其中 **1998 条含韩文**（需要翻译），980 条是 ASCII 标识符（如
  `item_amulet`、`gameobj_alchemist`，**必须保持原样**）。
- 这 1998 条按 50 条一批分成 40 批，由 40 个并行翻译代理译成繁体中文，
  每批自行对照字体字符表校验；随后统一跑校验器。
- 结果：**1998/1998 全部译出，0 条缺字、0 条标记丢失。**
- 保留了 `<CF3F300FF>` 之类的颜色标签、`%s`/`%d`/`%%` 格式符、`\n`、前后空格，位置不变。

### 2. `assets/*.csb` —— Cocos Studio 界面布局里的静态文字（123 条 / 38 个文件）

`.csb` 是**裸 FlatBuffers**。字符串结构为 `u32 长度 | UTF-8 字节 | NUL`，
由别处的 uoffset 引用（`target = ref_pos + u32(ref_pos)`）。

改法：`zh/csb.py` 先扫描**全部被引用的字符串**（忽略二进制噪声），
替换时把新串追加到缓冲区末尾并改写所有引用指针 —— 于是**长度可以自由变化**，
旧字节变成无人引用的残留，FlatBuffers 只按相对偏移读取，完全无影响。

覆盖了开场/结局旁白、主菜单（`普通模式`、`最高抵達層數`）、休息结算、成就页、魔法升级、
复活弹窗、优惠券、教学等界面。译文同样受字体字形限制。

### 3. 题材术语统一与质量校对

译文按暗黑地牢题材锁定了一套术语，并做了全量一致性审计（逐条比对韩文原词与中文用词）：

|---|---|---|---|

| 방어력 / 공격력 | **防禦力 / 攻擊力** | 24 / 15 | 一致（`방어`「防禦」与 `공격속도`「攻擊速度」属正常语境差异） |

`마법지식의 방`→魔法知識室、`무기지식의 방`→武器知識室、`무덤방`→墳墓房、`피라냐 방`→食人魚房、
`낭떠러지 방`→懸崖房間、`신전`→神殿、`기념관`→紀念館、`연금술방`→鍊金術房、`보물창고`→寶物倉庫、
`무기고`→武器庫、`서고`→書庫、`금고`→金庫、`제단`→祭壇、`석상실`→石像室、`묘소`→墓地、
`보물헌터의 방`→尋寶者之房、`무너진 방`→崩壞房間、`바리케이드 방`→路障房間、`농장`→農場、

**原地覆写并用 NUL 补齐**（如 `세미보스방` 15B → `準首領房` 12B + 3×NUL）。校验：改动

> 不会显示给玩家，故保持原样。

# 箱子经济修复（记忆之箱 / 广告 / 古代硬币）

## 1. 打完 Boss 不出记忆之箱 —— 根因是我们自己造成的

`UILayer::networking()` 的回包 22 处理器（`0x3c1b54`）有两条分支：

| result | 行为 |
|---|---|
| **0** | 把一件记忆道具写进玩家的 **6 格箱子数组**（`ProgressInfo+0x23C`，步长 12，`ProgressInfo::haveFreeBoxSpace()` 校验全部 6 格），并弹出 `UIGetCrystal` 取得动画 |
| 1 | 只推进流程（回主菜单 / `moveNewLevelSub()`） |

**之前的补丁为了让结算画面能关掉，把回包 22 一律写成 `result = 1` —— 于是每一次 Boss／通关奖励都被静默跳过了。** 这就是"打完 Boss 没有记忆之箱"的原因。

**修复**（`patchdefs.py` 的应答状态机）：回包 22 改为 `result = 0` 并填好载荷：

- `recvbuf[2..5]` = 扫描到的**第一个空箱位**（调用 `ProgressInfo::getInstance()` 后检查 `+0x23C`，6 格，负值即空位；全满则回落到 0）
- `recvbuf[6..9]` = 道具类型 **343 = 기억의 파편 / Piece of Memory**（游戏 204 字节道具表位于 `0x85336c`；同族还有 342 티끌、344 결정）。**必须用真实类型**，因为 `Item::getIconFilenameByItemType()` 不做越界检查
- `recvbuf[10..13]` = 回显请求里的层数（`sendbuf[7]`）
- `recvbuf[14..17]` 不需要：`getNewBoxGetType()` 已经改成直接读请求

载荷按**大端**写入（`ZPPTCPNetwork::getPacketInt()` 的约定），用 `rev` 转换。

## 2. 商店"看广告得免费箱子" —— 广告 SDK 已死

链路：`UIMessageBox::touchEvent`（`0x3c76d8`）→ `NativeWrapper::presentUnityAds()`（`0x3996d4`）→ `presentUnityAdsJNI`（`0x399454`）→ Java `show()`。SDK 不再投放，完成回调永远不来，所以奖励发不出去。

**修复**（`0x399454`，4 字节）：

```
30 b5 10 4c   ->   01 22 25 e0     ; movs r2,#1 ; b 0x3994a4
```

直接**尾跳**到 JNI 完成入口 `Java_..._onUnityAdsCompleted`（`0x3994a4`，只读 `r2`），走原本的奖励流程：事件 → 动画 → 激活记忆之箱 → 发送请求 27 → 回包 28 发古代硬币。是 `b` 不是 `bl`，栈与 `LR` 不变，目标函数自己的 `pop {…,pc}` 直接返回。

## 3. 600 古代硬币的箱子 —— 把价格改成 0

回包 14 处理器里扣 600 的立即数在**字面量池 `0x3c1ce8`**（全镜像仅此一处引用）：

```
a8 fd ff ff  (-600)   ->   00 00 00 00  (0)
```

纯数据，无编码/寄存器风险。

## 4. 成就奖励提高 10 倍

`GameNet::getAchievementReward()`（`0x3d6e38`）由 100 改为 **1000** 古代硬币（`movw r0,#1000; bx lr`）。每个成就仍只结算一次（处理器会调 `setAchievementCompleted`）。

## 5. 哪一个包有这些功能

广告箱子（请求 27）和 600 硬币箱子（请求 13）都需要**对应的请求被应答**：

| 构建 | 应答范围 | 箱子经济 |
|---|---|---|
| `*_offline_*`（完整版） | 除登录外全部 | **完整可用**（含开箱请求 9→10、符文/配方、复活等） |
| `*_safe_*`（保守版） | 仅 21、31 | 只修好 **Boss 记忆之箱**（21→22）与成就（31→32）；广告/600 硬币箱子的请求仍被吞掉 |

保守版**故意**保持最小应答面：回包 10 会用未经校验的箱子槽位索引写 `ProgressInfo`，正是当初把它排除的原因。想要完整箱子经济请用 **offline 版**。

## 6. 已知取舍：开箱槽位总是 0

回包 10（开箱）用 `getBoxOpenIndex()`（`recvbuf[2]`）算槽位：`ProgressInfo+0x244+12*idx`。
客户端在 `prepareOpenBox` 里把所选的箱子槽位写在 `sendbuf[7]`，但**本补丁的应答机故意不回显它**
（保持 0）。原因是该值经由一次虚函数调用传入、未做范围校验，一旦异常就是 `ProgressInfo` 越界写。
代价：开启时间戳总是记在槽位 0。若实测发现开启计时异常（例如反复免费开箱或某些箱子打不开），
可以改为回显客户端索引——功能更正确，但重新引入越界写风险，需要你确认后再动。
